# Review 06 — QA / Quality Architecture

*Reviewer role: senior QA engineer / quality architect.*
*Inputs reviewed: `docs/ANALYSIS.md` (2026-07-21), `docs/decisions/001-map-stack.md` (ADR-001).*
*Date: 2026-07-21. Project status: pre-code.*

---

## 1. Summary verdict

**Conditional GO.** The proposed architecture is unusually testable-by-design for a pre-code
document — append-only raw detections, an event-centric domain core behind ports & adapters, and
freshness as first-class data are exactly the seams a QA architect would ask for. However, the
proposal contains **no quality strategy at all**: no definition of alert correctness, no test
plan, no evaluation harness for the clustering parameters that *are* the product, and no release
discipline for a safety-adjacent service. For a product whose core tension is *false positives
erode trust / false negatives mean someone doesn't learn about a nearby fire*, correctness is a
feature with the same priority as the map itself.

The condition on the GO: the **alert correctness framework and the golden replay dataset
(§5.1–§5.2) must be built alongside the MVP, not after it**. Clustering parameters (DBSCAN
~2 km / 24 h) and the confidence score cannot be tuned or safely changed without them, and the
first fire season is the worst possible time to discover that.

---

## 2. Strengths

What the proposal gets right from a quality perspective — keep all of these:

1. **Append-only raw detections with explicit reprocessing intent** (ANALYSIS §5, decision 2).
   This is the single most important testability enabler in the whole design: it makes
   deterministic replay, shadow evaluation of new clustering parameters, and retrospective
   metric computation possible. Treat this as a hard architectural invariant.
2. **`FireEvent` as the core entity, behind ports & adapters.** The domain core (dedup,
   clustering, lifecycle, alert decisions) can be tested as pure logic with no network and no
   database. All the hard correctness logic lives on one side of a seam.
3. **Freshness as first-class data** (`last_observed_at`, "never imply live"). Staleness is
   observable and assertable, not an emergent UI accident. This turns the honest-UX ethic into
   a testable contract.
4. **Poll, don't stream, at MVP.** Polling is trivially fixture-able and replayable; the
   hardest adapter (FCI netCDF) is correctly deferred until demand is proven.
5. **The persistence rule already exists** ("≥2 detections before alerting default-sensitivity
   zones") — the design anticipates the false-positive problem rather than discovering it in
   production. It needs to be formalized into a measurable framework (§5.1), but the instinct
   is right.
6. **Explicit non-goals bound the quality obligation.** "Not a life-safety system", "no
   prediction modeling", "never send all-clear" — these limit the correctness surface we must
   guarantee and are the correct legal/ethical posture.
7. **ADR-001 is spike-aware.** Rejecting per-load tile pricing and planning PMTiles-on-R2
   means the *basemap* is already load-tested-by-construction; QA effort can concentrate on
   the parts we build (API, SSE, pipeline).
8. **Known false-positive sources are already enumerated** (sun glint, industrial heat,
   agricultural burns) with plausible mitigations (land-cover masking, persistence,
   confidence tiers). §5.2 turns each of these into a named regression scenario.
9. **The validation plan's step 1** (measure real FIRMS availability lag for a BG bbox) is
   precisely the data the QA framework needs to make replay realistic — run it and keep the
   raw output as a calibration artifact (§5.2).

## 3. Risks & gaps (severity-ranked)

Severity scale: **Critical** = can invalidate the product's core promise or cause harm;
**High** = will cause user-visible incidents or block safe iteration; **Medium** = will cause
rework or slow degradation; **Low** = manageable, note and move on.

### Critical

- **G1 — Alert correctness is undefined.** "Confidence score from source mix + persistence" is
  a phrase, not a specification. There is no definition of what a correct alert is, no metric,
  no threshold, and no measurement plan. Without this, "the alert engine works" is untestable
  and untunable, and the trust the whole business model depends on cannot be demonstrated.
  → §5.1 proposes the full framework.
- **G2 — Clustering parameters have no evaluation harness.** DBSCAN ~2 km / 24 h, merge/split,
  and lifecycle transitions are presented as constants, but they are the most behavior-defining
  numbers in the product. The document even says "clustering params will be tuned; must be able
  to re-run over history" — but specifies no dataset to tune *against*, no expected outcomes,
  and no comparison mechanism. Any parameter change silently changes who gets alerted.
  → §5.2 (golden dataset) + §5.7 (shadow mode).
- **G3 — No end-to-end latency budget.** The analysis is rigorous about *source* latency (3 h
  NRT, 10 min FCI) but says nothing about *our* pipeline latency: FIRMS row available → poll →
  cluster → enrich → alert dispatched → push delivered. A 5-min poller feeding a slow
  enrichment step or a backed-up outbox could add 30+ unmeasured minutes, and nothing in the
  design would notice. → §5.1 defines the budget and its measurement.

### High

- **G4 — Duplicate/flapping alert semantics are unspecified.** Events merge, split, cool, and
  reignite; later, FCI and FIRMS will detect the same fire at different resolutions. Every one
  of these transitions can re-trigger a geofence match. Nothing defines alert idempotency, a
  per-(zone, event) alert state machine, suppression windows, or what a merge means for zones
  already notified. Duplicate alerts are the fastest trust-killer after false positives.
  → recommendation R3, metrics in §5.1.
- **G5 — No production quality monitoring.** Nothing detects "pipeline silently broken":
  a poller that starts receiving empty-but-200 responses, a FIRMS CSV schema change, or a
  crashed clustering worker all present to users as *peace* — zero fires on the map during a
  heat wave. For this product, silent failure is indistinguishable from good news, which makes
  it a false-negative machine. → §5.5.
- **G6 — Notification delivery semantics are unspecified.** "Notification outbox" is named but
  at-least-once vs at-most-once, retry policy, dead-token handling, and delivery confirmation
  are not. A silently failing push adapter is a false negative for every affected user; a
  retry storm after an outage is a duplicate-alert incident. → R3/R4.
- **G7 — Time semantics are a latent bug farm.** FIRMS `acq_date`/`acq_time` are UTC; Bulgaria
  is UTC+2/+3 with a DST switch inside fire season shoulder; VIIRS passes cluster around
  ~01:30/13:30 local; the "24 h window" and the age classes ("new <6 h") all cross midnight
  and DST boundaries. None of this is called out, and it is exactly the class of bug unit
  tests must pin down. → §5.3, scenario S9 in §5.2.
- **G8 — There is no test strategy in the documents at all.** No mention of tests, CI,
  environments, or fixtures anywhere in ANALYSIS.md or ADR-001. For a solo-evenings MVP this
  is understandable, but it must not survive first code. → §5.3 defines the pyramid; §5.7 the
  gates.

### Medium

- **G9 — Geodesy/CRS pitfalls in the +100 km cross-border scope.** DBSCAN "2 km" must be 2 km
  *in meters* (haversine or a projected CRS), not degrees — at 42°N, 1° of longitude ≈ 82.7 km
  vs 111 km latitude, so degree-based eps is anisotropic and wrong. Likewise geofences must
  use PostGIS `geography` (or an explicit projection), not `geometry` in EPSG:4326, for
  `ST_DWithin` in meters. Cheap to get right on day one, expensive to migrate later.
- **G10 — Source field heterogeneity is untested-by-design.** FIRMS confidence is *numeric
  0–100 for MODIS* but *categorical l/n/h for VIIRS*; the brightness columns differ by source
  (`brightness`/`bright_t31` vs `bright_ti4`/`bright_ti5`); `acq_time` is `HHMM` where a naive
  numeric parse turns `0005` into `5`. The normalization layer needs an explicit contract and
  edge-case unit tests. → §5.3.
- **G11 — FIRMS API failure modes return 200.** The area API is known to return plain-text
  bodies (invalid key messages, rate-limit notices) and empty-but-valid responses with HTTP
  200. "HTTP 200 = success" is wrong for this adapter; the parser must validate the CSV header
  before trusting the body. → §5.3, §5.5 (schema-drift detector).
- **G12 — Frontend/map QA is absent, and one invariant is load-bearing.** ADR-001's "red/
  orange reserved exclusively for fire layers" is a genuinely good safety-UX rule with no
  enforcement mechanism, and color-only encoding of age/intensity excludes ~8% of male users
  (deuteranopia/protanopia) from the product's core signal. → §5.4 proposes automated checks
  for both.
- **G13 — SSE at spike scale is unexamined, and "serverless" conflicts with it.** ANALYSIS §5
  offers "one small VM or serverless" — long-lived SSE connections are hostile to most
  serverless runtimes (execution time limits, per-connection billing). Pick the VM for the SSE
  tier, and soak-test it before the season. → §5.6.
- **G14 — Security/privacy testing obligations are implied but not stated.** Watch zones are
  home locations (GDPR-sensitive, correctly noted). That implies concrete authz tests (user A
  must never read user B's zones or alert history), deletion tests, and no-location-in-logs
  checks. → R8.

### Low

- **G15 — OpenFreeMap no-SLA is accepted without a tripwire.** Fine pre-launch, but add a
  synthetic check (fetch one tile every 5 min; alert on failure) so the Phase-2 migration
  decision is triggered by data, not by an outage during a fire.
- **G16 — Dark mode doubles the visual test matrix.** Plan the visual-regression state list
  (§5.4) to include both variants from the start, or dark mode will rot.

## 4. Detailed recommendations

Numbered, mapped to gaps, ordered by when they should happen.

- **R1 (G1, G3 — before first alert ships):** Adopt the alert correctness framework in §5.1:
  metric definitions, the latency budget decomposition, and the MVP acceptance thresholds.
  Publish the thresholds in the repo (`docs/quality/metrics.md` or similar) so they are a
  contract, not folklore.
- **R2 (G2, G8 — alongside first pipeline code):** Build the golden replay dataset (§5.2)
  from 2024–2025 FIRMS archive days *before* tuning any clustering parameter. The replay
  harness is the unit under which clustering is developed, not a later add-on. Budget: ~2–3
  evenings for the harness, ~1 evening per scenario fixture.
- **R3 (G4, G6):** Specify the alert state machine per `(zone_id, event_id)`:
  `none → notified_new → notified_escalation → cooldown`, with an idempotency key
  `(zone_id, event_id, alert_type)` enforced by a unique constraint in the outbox, an explicit
  suppression window (propose: no repeat of the same alert type for the same pair within
  6 h), and defined merge semantics (a merged event inherits the notified state of *all*
  parents — a merge is never a "new fire" for an already-notified zone). Outbox is
  at-least-once with idempotent dispatch; dead push tokens are pruned on permanent provider
  errors and surfaced as a metric.
- **R4 (G6):** Make delivery observable: every alert row records `decided_at`,
  `dispatched_at`, `provider_ack_at`, `status`. The latency budget in §5.1 is measured from
  these timestamps; a stuck outbox alarms (§5.5).
- **R5 (G7, G9, G10, G11):** Write the "boring correctness" unit-test batteries of §5.3 first
  (time, geodesy, CSV parsing, confidence normalization). These are cheap, fast, and cover
  the majority of realistic field bugs in this domain.
- **R6 (G5):** Stand up the production quality monitors of §5.5 *at MVP launch*, not v1. The
  zero-detections-during-heat-wave tripwire and the source-staleness alarm are two cron jobs
  and a webhook — hours of work, existential value.
- **R7 (G12):** Implement the two automated frontend checks in §5.4 (style-lint for the
  fire-owns-red rule; CVD-simulation palette check) as CI scripts. Both run in <1 s and
  protect invariants that manual review will eventually miss.
- **R8 (G14):** Add an authz/privacy test suite to the integration layer: cross-tenant zone
  access is denied (API-level tests), account deletion cascades to zones and push tokens,
  and a log-scrubbing check that zone coordinates never appear in application logs at
  info-level.
- **R9 (G13):** Commit to the VM (not serverless) for the SSE/API tier at MVP, and run the
  §5.6 soak battery before the first advertised fire season.
- **R10 (G2, safety):** Adopt the release regime of §5.7 — fire-season deploy gates, feature
  flags for any alert-logic change, and shadow-mode rollout for clustering changes. This is
  the process answer to "we must tune parameters on a live safety-adjacent system".

## 5. QA deep dive

### 5.1 Alert correctness framework

#### 5.1.1 The measurement problem

There is no authoritative real-time ground truth for "there is a fire at X". The framework
therefore uses **retrospective proxies**, each biased in a known direction, and triangulates:

| Truth proxy | What it gives | Bias / limitation |
|---|---|---|
| **EFFIS burnt-area perimeters** | Polygons + date ranges for fires that left a mappable scar (reliably ≥ ~30 ha; verify current threshold) | Misses small/short fires → usable for **recall** of significant fires, weak for precision of small events |
| **Curated news/official log** | Human-confirmed incidents (ГДПБЗН bulletins, regional media), manually maintained table: `date, approx location, name, source URL` | Labor (~30 min/week in season); biased toward populated areas → good **precision** check for alerted events |
| **Self-consistency (persistence)** | An event corroborated by later detections (different overpass or source) is very likely real | Circular for recall; good cheap precision signal |
| **FIRMS' own map / API** | The unprocessed source | Only validates our *ingestion*, not our event logic |

#### 5.1.2 Metric definitions

All metrics are computed per calendar week in season, over the full AOI and per-zone where
noted. "Alertable event" = a FireEvent that meets the default-sensitivity alert criteria
(regardless of whether any user zone actually matched).

| ID | Metric | Definition (formula) | Truth source | Cadence |
|---|---|---|---|---|
| **PCR** | Perimeter Coverage Rate (recall proxy) | Of EFFIS BA perimeters ≥ N ha intersecting the AOI, the fraction for which we had a FireEvent whose detections intersect the perimeter buffered by 2 km, with event start ≤ perimeter end date. Report for N = 50 and N = 10. | EFFIS BA | Weekly, retro |
| **CER** | Corroborated Event Rate (precision proxy) | Of our alertable events, the fraction corroborated within 7 days by ≥1 of: (a) EFFIS BA overlap as above, (b) ≥2 additional detections in later overpasses, (c) an entry in the curated news log within 5 km / ±1 day. | All three | Weekly, retro |
| **ZAP** | Zone Alert Precision | Of alerts actually dispatched, fraction whose triggering event was corroborated (same rule as CER). This is the user-experienced precision. | All three | Weekly, retro |
| **DAR** | Duplicate Alert Rate | Alerts that repeat the same `(zone, event, alert_type)` semantic content within the suppression window ÷ total alerts dispatched. Merge/split re-notifications count as duplicates unless they carry an escalation. | Our own logs | Continuous |
| **FLR** | Flapping Lifecycle Rate | Events with ≥3 lifecycle direction reversals (active→cooling→active→cooling) within 48 h ÷ active events. High FLR predicts duplicate alerts and UX distrust. | Our own logs | Continuous |
| **PLB** | Pipeline Latency Budget compliance | See decomposition below; p50/p95 per stage from recorded timestamps. | Our own logs | Continuous |

#### 5.1.3 Latency budget (the part we control)

Every detection and alert carries stage timestamps. Budget is for the **controllable
pipeline** — source latency (up to ~3 h NRT) is measured, displayed honestly, but not budgeted.

| Stage | Timestamps | Budget (p95) |
|---|---|---|
| FIRMS row available → ingested | `available_at`* → `ingested_at` | ≤ poll interval + 2 min (≤ 12 min at 10-min polling) |
| Ingested → event created/updated | `ingested_at` → `event_updated_at` | ≤ 60 s |
| Event updated → alert decision | `event_updated_at` → `decided_at` | ≤ 10 s |
| Alert decision → provider ack | `decided_at` → `provider_ack_at` | ≤ 60 s (push), ≤ 5 min (email) |
| Event updated → SSE broadcast sent | `event_updated_at` → broadcast | ≤ 2 s |
| **Total controllable, detection row → push ack** | | **≤ 15 min p95** |

\* `available_at` is approximated as the poll time of the first poll that returned the row;
the validation-plan step 1 script should also record it to calibrate replay (§5.2).

Additionally track (report, don't budget): `acq_time → available_at` (source latency) —
this is the number that goes into the honest-freshness UX and marketing claims.

#### 5.1.4 MVP launch acceptance thresholds (initial proposal — calibrate on golden dataset)

Gate: do not enable public alerts until all of these hold over a 2-week measurement window
(live shadow period, alerts computed but sent only to the team):

- **PCR ≥ 95 %** for EFFIS perimeters ≥ 50 ha; **≥ 85 %** for ≥ 10 ha. (A significant fire we
  never evented is the worst failure class.)
- **CER ≥ 80 %** for alertable events; **ZAP ≥ 85 %** (alerts are gated harder than events).
- **DAR ≤ 5 %** during shadow; target ≤ 1 % steady state.
- **PLB total ≤ 15 min p95**; no stage red for >1 day.
- **Zero** alerts triggered by a single low-confidence detection at default sensitivity
  (assert as an invariant test, not a metric).
- **Zero** "all clear"-semantics messages anywhere in alert copy (checklist item, §5.7).

Thresholds are deliberately asymmetric: recall of *big* fires is near-absolute; precision is
allowed to cost some sensitivity because the map (unlike alerts) still shows low-confidence
detections with a visible confidence tier — the user-facing distinction between "on the map"
and "worth an alert" is the product's main precision/recall dial and should be documented as
such.

### 5.2 Golden-dataset strategy

#### 5.2.1 Principle

Every correctness claim about clustering, lifecycle, and alerting is made against **replayable
fixtures built from real historical Bulgarian fire days**, sourced from the FIRMS archive
(`_SP` standard-processing sources; note SP is reprocessed and may differ slightly from what
NRT served on the day — acceptable; additionally keep at least one *recorded live NRT* day
captured by the validation-plan poller for realism).

#### 5.2.2 Fixture format

```
fixtures/
  s01-border-crossing-slavyanka/
    manifest.json          # id, name, AOI bbox, time range [T0,T1], sources, provenance URLs
    firms/
      viirs-snpp.csv       # full archive CSV for AOI+time range, original columns untouched
      viirs-noaa20.csv
      modis.csv
      availability.json    # per-row availability offsets: acq_time -> available_at
                           # (sampled from the measured NRT lag distribution; deterministic seed)
    effis/
      ba-perimeters.geojson  # burnt-area truth for the window (for metric assertions)
      wms-danger/*.png       # recorded GetMap responses if the scenario needs the overlay
    open-meteo/
      {lat}_{lon}_{date}.json  # recorded wind/temp responses keyed by request
    zones.json             # synthetic test watch zones with sensitivity settings
    expected.json          # assertions (below)
```

`expected.json` asserts **outcomes, not internals**:

```json
{
  "events": [
    { "match": "near 41.42,23.60 r=5km", "created_by": "2024-08-12T11:00Z",
      "lifecycle": ["new","active","cooling","active","out"],
      "min_detections": 40, "crosses_border": true }
  ],
  "merges": [ { "at_or_before": "…", "result_event": "…" } ],
  "alerts": [
    { "zone": "z-petrich", "type": "new_fire", "by": "2024-08-12T12:00Z" },
    { "zone": "z-sofia-control", "type": "none" }
  ],
  "invariants": [ "no_duplicate_alerts", "no_alert_from_single_low_conf" ]
}
```

#### 5.2.3 Replay mechanics (determinism contract)

The replay driver owns a **virtual clock**. Each poller port is replaced by a fixture adapter
that, at virtual time T, returns exactly the rows with `available_at ≤ T` not yet served —
modeling the ~3 h NRT lag is mandatory, otherwise replay is unrealistically prompt and hides
ordering bugs. Determinism requirements on the production code (enforce via the harness):

1. No wall-clock reads in the domain core — clock is an injected port.
2. Stable, documented ordering of detection processing (e.g. by `available_at, source, lat, lon`).
3. No RNG in clustering (DBSCAN is deterministic given ordering — keep it that way).
4. Replay of the same fixture twice yields byte-identical event timelines and alert logs
   (assert this in CI: run each fixture twice, diff).

The E2E variant (§5.3) runs the same fixtures through the *fully assembled* app (real PostGIS,
real Fastify, real SSE) with only the HTTP adapters and clock swapped.

#### 5.2.4 Named scenarios (must-cover set)

Candidate real-world basis given as "e.g." — pin exact dates from the FIRMS archive when
building each fixture; the scenario contract is what matters.

| ID | Scenario | Real-world basis (candidate) | Exercises | Key assertions |
|---|---|---|---|---|
| S1 | **Fire crossing the BG–GR border** | Slavyanka/Ali Botush border fire, Aug 2024 (spread from Greece) | +100 km buffer ingestion, cross-border clustering, geofences near border | One continuous event though centroid is in GR; BG zones near border alerted; no event split at the border line |
| S2 | **Two nearby fires merging** | Sakar/Harmanli region, late Jul 2024 (multiple ignitions) | Merge semantics, event identity, alert dedup | Merge produces one event inheriting notified state; no second "new fire" alert to already-notified zones; detection history preserved from both parents |
| S3 | **Agricultural burn false positive** | Stubble burning, Dobrudzha cropland, any July week | CORINE/WorldCover land-cover masking, confidence tiers | No default-sensitivity alert; detection visible on map in low-confidence tier; CER not charged (excluded class) |
| S4 | **Industrial heat source** | Persistent hotspot at a known industrial site (e.g. Maritsa Iztok complex; Pirdop smelter; refinery flare) | Static-source suppression (known-source list and/or persistence-without-spread heuristic) | Never alertable; flagged `static_source`; still counted in pipeline-liveness canary (§5.5) |
| S5 | **Single-detection noise** | Any lone low-confidence VIIRS pixel never re-observed | Persistence rule, event expiry | No alert; event (if created at all) expires without lifecycle noise; invariant `no_alert_from_single_low_conf` |
| S6 | **Multi-day megafire, cooling + reignition** | A 2025 multi-day fire (BG was #3 in EU 2025; pick from archive) | Lifecycle new→active→cooling→active, reignition alerting | Reignition raises an *escalation* alert, not a duplicate "new fire"; age-class encoding transitions correct across days; FLR = 0 for this event |
| S7 | **Cloudy-gap day during an active fire** | Overcast day inside S6's window | Absence-of-detections handling | Event does not flip to `out` merely for missed passes; staleness surfaces in `last_observed_at`; no "all clear" implication anywhere |
| S8 | **Source outage / stale poll** | Synthetic: FIRMS adapter returns errors/empty-200 for 6 h inside S2 | Poller resilience, staleness UX, recovery backfill | No event corruption; staleness flagged within one poll interval; recovery ingests backlog without duplicate alerts |
| S9 | **UTC/DST boundary day** | Synthetic: detections straddling 00:00 UTC and the DST switch | Time semantics (G7) | Age classes and 24 h windows computed correctly; `acq_time` `0005` parsed as 00:05 |

S1–S6 are the mandated minimum; S7–S9 are cheap synthetics that close gaps G5/G7 and are
strongly recommended in the same batch.

### 5.3 Test pyramid for the geospatial pipeline

#### Unit (fast, pure, hundreds of cases — the bulk)

- **Clustering math:** haversine/projected distance correctness at 42°N (assert 2 km eps means
  meters, not degrees — G9); DBSCAN membership at eps boundary; merge and split cases; temporal
  window edges (detection at exactly 24 h); lifecycle transition table exhaustively
  (new/active/cooling/out × new-detection/timeout/reignition).
- **FIRMS CSV parsing edge cases:** header-only file; completely empty body; plain-text error
  body with HTTP 200 (invalid key / rate-limit text) — parser must validate the header row
  before trusting content; CRLF vs LF; unknown extra columns (schema drift tolerated + flagged);
  MODIS vs VIIRS column sets (`brightness`/`bright_t31` vs `bright_ti4`/`bright_ti5`);
  confidence normalization (numeric 0–100 vs categorical `l`/`n`/`h` → one internal scale);
  `acq_time` `"0005"` → 00:05 (never numeric-parse); coordinates out of bbox; duplicate rows
  across overlapping polls (dedup key: source + satellite + acq timestamp + rounded coords).
- **Alert decision function:** pure function `(event, zone, alertHistory) → decision`;
  property-style tests for the invariants (single low-conf never alerts; suppression window
  honored; merge inherits notified state).
- **Time:** all of G7 as table-driven tests.

#### Integration (real infrastructure, seconds each)

- **Real PostGIS via Testcontainers** (`postgis/postgis:16-3.x` image, `@testcontainers/
  postgresql`): `ST_DWithin` on `geography` for geofence matching (assert meters semantics);
  clustering support queries; migration up/down; outbox unique-constraint idempotency;
  append-only detections constraint (no UPDATE/DELETE grants on the table).
- **Recorded HTTP fixtures** for each adapter (nock or Polly.JS): FIRMS happy path + all G11
  failure modes; EFFIS WMS GetMap (recorded PNG + capability XML); Open-Meteo responses +
  timeout/5xx; retry/backoff behavior; etag handling on the poller.
- **Notification adapter contract tests:** provider stubs asserting idempotency-key
  propagation, permanent-failure token pruning, retry classification.
- **Authz suite (R8):** cross-tenant zone access denied at API level; deletion cascades.

#### End-to-end (few, high-value)

- **Golden replay E2E:** each §5.2 fixture through the assembled app; assert (a) REST GeoJSON
  matches `expected.json`, (b) an SSE client receives event create/update/merge messages in
  order and within the §5.1 broadcast budget, (c) outbox contents match expected alerts.
- **One Playwright smoke:** app boots against a replayed fixture; map renders; an event marker
  exists; detail panel opens and shows detection history and freshness line. Chromium +
  WebKit, one mobile viewport.

#### Explicitly NOT automated at MVP

- Full cross-browser matrix (Chromium + WebKit smoke only; no Firefox/legacy).
- Pixel-perfect basemap rendering across all zooms (only the §5.4 named visual states).
- Real push delivery to physical devices (contract-test the adapter; manually verify one push
  per release on one Android + one iOS device — a 2-minute checklist item).
- FCI netCDF decoding (not in MVP; build its fixtures during the planned spike instead).
- Load/chaos battery in CI (run pre-season and on infra changes — §5.6 — not per-PR).
- Screenshot-testing the EFFIS WMS overlay content (we don't own it; assert only that the
  layer toggles and the recorded GetMap URL shape is correct).

### 5.4 Map & frontend QA

- **Visual regression (deterministic):** Playwright `toHaveScreenshot` with all variability
  pinned: local fixture tiles (small Balkans PMTiles extract served by the test server — no
  network), pinned style JSON, fixed seed data (fabricated GeoJSON with every age/intensity
  class), animations off, fixed viewport. Named states (× light/dark = 12 shots): empty map;
  events-all-classes; event selected + panel; danger WMS overlay on; cluster zoomed out;
  mobile 360×640 events view. Diff budget `maxDiffPixelRatio: 0.01`.
- **"Fire owns red" as a CI lint (G12):** a script that loads the style JSON, extracts every
  paint color (`fill-color`, `line-color`, `text-color`, `background-color`, including
  data-driven expression outputs), converts to OKLCH, and **fails if any layer whose id is not
  prefixed `fire-`/`alert-` has hue ∈ [20°, 55°] ∪ [350°, 360°] with chroma > 0.09**. Runs in
  <1 s on every style change; the thresholds live next to the script with a documented
  exemption list (expected: none).
- **Viewport/mobile matrix (manual + smoke):** supported set — 360×640 (budget Android — the
  primary rural user), 390×844 (iPhone), 768×1024 (tablet), 1280+ (desktop); Chromium + WebKit.
  Touch targets ≥ 44 px on event markers and panel controls. Performance budget: map
  interactive ≤ 10 s on "Fast 3G" throttle with cold cache (rural connectivity is in ADR-001's
  own requirements — hold it to that).
- **Color-blind-safe encoding of age/intensity (concrete check):** rule first, check second.
  *Rule:* age/intensity is never encoded by hue alone — new/active/cooling differ additionally
  by **size and symbol/halo** (e.g. new = large pulsing halo, active = filled circle, cooling
  = smaller hollow circle), and the detail panel states the class in text. *Check:* a CI
  script (culori + a CVD simulation lib) simulates deuteranopia, protanopia, and tritanopia
  over the fire palette and asserts pairwise ΔE00 ≥ 15 between adjacent classes *under each
  simulation*; if the palette alone fails (it will, red/orange hues collapse under
  deuteranopia), the script asserts the style defines the redundant channel (distinct
  `circle-radius`/symbol per class) — i.e., the check passes on *color-or-shape*, never
  requires color alone to carry it.
- **Alert UX accessibility:** SSE-driven updates announced via a polite `aria-live` region
  ("New fire event 12 km from Harmanli"); WCAG AA contrast on panel text over both themes;
  axe-core (via `@axe-core/playwright`) on the non-canvas surfaces (panel, list, settings) in
  the smoke run. The WebGL canvas itself is exempt; its information must be reachable through
  the DOM panel — that duplication is the accessibility strategy.

### 5.5 Production quality monitoring

The theme: for this product, **silence must be suspicious by default**.

- **Ingestion parity vs FIRMS (continuous):** hourly job fetches the same bbox from FIRMS and
  compares row count + max `acq_time` against what we ingested. Any deficit > 0 sustained for
  2 cycles = ingestion bug alarm. This catches parser regressions and silent poller death.
- **Event parity vs EFFIS (daily, in season):** compare our active events against EFFIS
  active-fire/BA layers; discrepancies feed the weekly PCR/CER computation (§5.1) and a daily
  "unmatched significant perimeter" alarm (any new EFFIS perimeter ≥ 50 ha with no
  corresponding event = investigate today, not at the weekly review).
- **Canary zones (fixed, internal-only):**
  - *Hot canary:* a geofence over a known persistent industrial heat source (S4's site). It
    should register detections regularly; **no detections for > 72 h ⇒ pipeline-liveness
    alarm** (alerts for it are suppressed publicly but logged internally).
  - *Cold canary:* a geofence over a zero-expectation area (e.g. open water/high bare rock).
    Any alertable event there ⇒ false-positive tripwire, page immediately.
  - *Synthetic end-to-end canary:* nightly, inject one synthetic detection at a reserved test
    location through the real pipeline into a test-only alert channel; measures true
    detection→push latency daily and proves the outbox path.
- **Alert-on-anomaly:** (a) **zero detections in the whole AOI for > 36 h while the EFFIS FWI
  danger layer shows high/very-high/extreme anywhere in the AOI ⇒ treat as pipeline bug, not
  peace** — page; (b) source staleness: age of last successful FIRMS fetch > 3× poll interval
  ⇒ warn, > 2 h ⇒ page, and surface staleness in the public UI (the honest-UX promise);
  (c) CSV schema-drift detector: hash of the header column set per source; change ⇒ warn +
  quarantine parsing to tolerant mode; (d) detection-count z-score vs a rolling seasonal
  baseline (day-of-year ± 7 d) — both tails alarm.
- **Minimum metric set** (Prometheus-style): `poll_last_success_timestamp{source}`,
  `detections_ingested_total{source}`, `events_active`, `event_update_latency_seconds`,
  `alert_dispatch_latency_seconds` (histogram, per stage per §5.1.3), `outbox_pending`,
  `outbox_failed_total{reason}`, `sse_clients`, `sse_broadcast_latency_seconds`,
  `tile_synthetic_check_up` (G15).
- **Weekly quality report:** automated job computes PCR/CER/ZAP/DAR/FLR/PLB into a dated
  markdown/dashboard entry; 15-minute human review is a standing season ritual.

### 5.6 Load & chaos testing (matched to the spike profile)

**Profile to design for:** the Watch Duty lesson — load arrives as a step function during a
disaster, exactly when failure is most costly. MVP targets (revise with real traffic data):
**5,000 concurrent SSE clients** and **200 req/s REST GeoJSON** on the MVP VM, with headroom
documented (at what N does it fall over — measured, not guessed).

- **Tools:** **k6** for REST (native) and for SSE via the **`xk6-sse` extension** (core k6
  has no SSE support — build a custom k6 binary with `xk6 build --with
  github.com/phymbert/xk6-sse`). Fallback/alternative: a plain Node soak driver using
  `undici` + `EventSource` for SSE (simpler than teaching Artillery SSE; Artillery remains an
  option for REST scenarios if k6 is disliked). Toxiproxy for network-fault injection between
  app and Postgres and between poller and a FIRMS stub.
- **SSE soak test:** ramp to 5k connections over 10 min, hold **2 h**, while the replay
  harness injects an event update every 30 s. Pass: p95 broadcast latency ≤ 2 s throughout;
  server RSS growth ≤ 10 % after the first 15 min (no per-connection leak); 0 dropped events
  for connected clients; reconnect storm (drop 10 % of clients/min for 10 min, all reconnect
  with `Last-Event-ID`) recovers with no missed or duplicated events.
- **API load:** 200 req/s mixed GeoJSON reads (bbox queries, event detail) for 30 min. Pass:
  p95 ≤ 300 ms, error rate ≤ 0.1 %, Postgres connections stable (pool bounded).
- **Poller failure injection (chaos):** against the assembled app with a scripted FIRMS stub:
  (a) 500s for 30 min; (b) timeouts; (c) empty-200; (d) HTML error page with 200; (e) valid
  CSV with a new column; (f) **stale-source simulation** — same etag/content for 6 h. Pass
  criteria: staleness visibly flagged (API field + UI) within one poll interval; monitors of
  §5.5 fire as specified; no event-state corruption (post-chaos replay diff is clean); on
  recovery, backfill ingests the gap **without emitting duplicate alerts** (idempotency keys
  hold); poller never tight-loops (backoff verified).
- **Database chaos:** kill/restart Postgres mid-poll and mid-alert-dispatch; pass: outbox
  delivers exactly the pending alerts after recovery (at-least-once with idempotent dispatch
  = no user-visible duplicates), no half-written events.
- **Cadence:** full battery before each fire season and after infra changes; SSE soak also
  after any change to the SSE/broadcast code path. Not in per-PR CI.

### 5.7 Release process for a safety-adjacent product

**Two regimes:**

- **Off-season (≈ Oct 15 – May 31):** normal continuous delivery. CI gates: unit +
  integration + golden replay suite green (including the determinism double-run diff), style
  lint + CVD check, authz suite.
- **Fire season (≈ Jun 1 – Oct 15):** everything above, plus the deploy gate checklist below,
  no deploys Friday/weekend/evenings except hotfixes, and **no changes to alert logic outside
  the flag + shadow process**.

**Fire-season deploy gate checklist (all boxes or no deploy):**

- [ ] Golden replay suite green, including S1–S9.
- [ ] No *active severe event*: no currently-active event ≥ threshold FRP/size in the AOI and
      EFFIS danger not "extreme" over a populated area — otherwise deploy waits (hotfix path
      exempt, requires the second checkbox owner's ack).
- [ ] Migration is expand-contract (no destructive step in the same deploy).
- [ ] Alert-logic diff = none, OR change is behind a flag defaulting to old behavior.
- [ ] Rollback rehearsed for this release (one-command, < 5 min, outbox idempotency keys
      guarantee no alert re-sends on reprocessing).
- [ ] Kill switches verified in staging: global alert pause (with public status banner) and
      per-source disable flags.
- [ ] Post-deploy watch: 30 min on the §5.5 dashboard; synthetic E2E canary triggered
      manually once.
- [ ] One real push received on a physical device (the 2-minute manual check from §5.3).

**Feature flags for alert logic:** every change to clustering parameters, confidence scoring,
suppression windows, or alert copy ships as **versioned config-as-data**
(`clustering_params_v3`, etc.) behind a flag; the running system logs which version produced
every event and alert (auditability — also a future B2B/SLA requirement).

**Shadow-mode rollout of new clustering/alert parameters:**

1. Candidate version runs **in parallel** on the same detection stream, writing to shadow
   tables (`events_shadow`, `alerts_shadow`); it **never dispatches** anything.
2. Nightly automated diff report: events created/merged/split, alerts that *would* have
   fired, per-zone deltas, projected PCR/CER/DAR movement.
3. Promotion criteria: ≥ 7 consecutive season-days (or ≥ 14 off-season) in shadow; every diff
   line explained; golden replay non-regression (old fixtures still pass, or `expected.json`
   consciously updated with a reviewed rationale); projected metrics within §5.1 thresholds.
4. Staged enablement: team zones → volunteer beta zones → all zones; DAR and ZAP watched at
   each stage; instant revert = flag flip.

This is the process answer to G2: the parameters *will* be tuned during live seasons, and
shadow mode is what makes that safe.

## 6. Open questions for the team

1. **Confidence score formula:** what exactly combines source mix + persistence + land cover
   into the score, and where does the alertability threshold sit? This needs an owner and a
   written spec before §5.1 metrics can gate it.
2. **Event "out" semantics:** after how many detection-free hours (and how many *expected
   passes*, given clouds — S7) does an event become `out`? Is `out` ever shown, given the
   "never send all-clear" rule?
3. **Merge/split identity contract:** which event ID survives a merge, and is event ID
   stability a public promise (it becomes one the moment the v2 B2B API exists)?
4. **Alert taxonomy:** what alert types exist at MVP (`new_fire`, `escalation`, anything
   else)? What does a user-facing "sensitivity" setting actually change — persistence count,
   confidence floor, radius?
5. **Who curates the news/official truth log** (~30 min/week in season), and who reviews the
   weekly quality report? For a solo project this is the founder — say so explicitly and
   timebox it.
6. **Delivery SLO:** is there a target for push delivery success rate, and how are dead
   tokens/opt-outs measured against it?
7. **Staging environment:** will there be a staging instance polling real FIRMS continuously
   (recommended — it doubles as the shadow-mode host and the latency measurement source), and
   does the free-tier budget (€10–30/mo) cover it?
8. **FCI fusion dedup (v1):** when the geostationary stream arrives, the same fire appears in
   two sources at different resolutions/cadences — what is the cross-source dedup design, and
   which golden scenarios get added? (Flagging now so the Detection schema reserves what
   fusion needs — e.g. per-source pixel footprint, not just a point.)
9. **Alert copy sign-off:** who reviews alert wording for panic-minimization and the legal
   disclaimer set (ANALYSIS §6.4), and is that review a release-gate checkbox? (Proposed:
   yes — add to §5.7 checklist once copy exists.)
10. **On-call reality:** during fire season, what is the honest response time to a §5.5 page
    for a solo operator, and is that stated in the product's terms (it should inform how
    strongly the "not a life-safety system" disclaimer is worded)?
